# Implementation Plan: Agents as Tools (Multi-Agent Delegation)

**Branch**: `008-agents-as-tools` | **Date**: 2026-05-11 | **Spec**: [spec.md](./spec.md)
**Input**: Feature specification from `/specs/008-agents-as-tools/spec.md`

## Summary

Allow any agent (built-in or custom) to declare other agents as callable tools. At runtime, each referenced sub-agent is wrapped via the Microsoft `agent-framework` `Agent.as_tool()` API and added to the parent agent's tool list — the same pattern shown in the upstream `client_with_agent_as_tool.py` sample. The Custom Agent Builder gets a new "Agents as Tools" section (alongside Tools, AI Search Context, Skills, MCP Servers, Starter Questions), and all subsection headers are restyled so they read clearly as subordinate to the page title.

Approach in one sentence: extend the agent profile schema with an optional `agents_as_tools: list[SubAgentToolRef]` field, resolve each reference into a fully-built `RuntimeAgent` inside `agent_factory.create_chat_runtime`, call `.as_tool(...)` on it, and append the result to `all_tools` — with frontend-side resolution of custom-agent references (since custom agents live in `localStorage` today) and dual-layer validation (frontend form + backend validators) for self-reference, direct A↔B cycles, duplicate tool names, and tool-name format.

## Technical Context

**Language/Version**: Python 3.12+ (backend), TypeScript / React 18 (frontend)
**Primary Dependencies**: FastAPI, `agent-framework-core` (`Agent.as_tool()`), `agent-framework-azure-ai-search`, OpenAIChatClient (Azure OpenAI Government endpoint), React, Vite
**Storage**: Built-in agents → `config/agents.yaml`. Custom agents → frontend `localStorage` (key `webagents_custom_agents`). No backend custom-agent store today; the new field is purely additive to the existing in-memory / localStorage shapes.
**Testing**: `pytest` (backend, run via `uv run pytest`), Vitest / React Testing Library (frontend), Playwright for visual verification
**Target Platform**: Single Azure App Service serving FastAPI backend + built React static assets (Azure Government cloud)
**Project Type**: Two-tier web application (existing structure — Python backend at repo root, React app in `frontend/`)
**Performance Goals**: No new perf budget. Sub-agent invocation adds one nested LLM round-trip per tool call; user-perceptible latency target stays the same as a regular tool call (no streaming of intermediate sub-agent tokens — explicit non-goal per spec).
**Constraints**: No data-mutation tools introduced (Constitution I respected). Sub-agent references resolved by stable ID; renaming an agent must not break references. Custom-agent persistence remains client-side localStorage — no backend storage added in this feature (Constitution V — minimalism).
**Scale/Scope**: Small — a typical parent agent has 0–5 sub-agent references; total registered agents per deployment is single-digit (built-ins) plus a handful of custom agents per admin.

## Phase 0 — Research

See [research.md](./research.md). Resolves:

1. Exact `agent-framework` `Agent.as_tool()` signature and behavior (return type, `arg_name` / `arg_description` semantics, error surfacing).
2. Whether the `RuntimeAgent` produced by `OpenAIChatClient.as_agent()` exposes `.as_tool()` directly (the upstream sample constructs `Agent(...)` explicitly — confirm parity).
3. How to serialize sub-agent references for built-in vs custom agents in a single uniform payload, given custom agents live in frontend `localStorage` today.
4. Visual styling baseline — what consistent CSS rule set unifies the existing six (soon seven) subsection headers without a redesign.
